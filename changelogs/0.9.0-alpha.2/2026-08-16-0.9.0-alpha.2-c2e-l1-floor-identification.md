# C2E: L1 OS-boundary identification via system-header classification

Implements the floor-identification mechanism from the C2E floor-thinning plan
(`docs/plans/tooling/c2e-floor-thinning-handover-2026-08-16.zh-CN.md` §2):
clang already distinguishes project headers (`-I`) from system headers
(`-isystem`), and declarations in system headers have no translatable C source
— that is exactly the L1 OS binary boundary (Win32/GL/libc).

- `ClangNative` exports `clang_Location_isInSystemHeader`;
  `ClangSession.Parse` accepts `systemIncludePaths` and forwards them as
  `-isystem` arguments.
- `CBodyTranslator.Translate` gains a `systemIncludePaths` parameter and
  classifies every extern candidate (`PendingExtern`) at its declaration site:
  system header → `IsFloor` (L1 binary boundary), otherwise cross-TU project
  symbol. `C2EResult` exposes the resulting `FloorSymbols` /
  `CrossTuSymbols` lists (conservative over-approximation: externs recorded
  during fixpoint retries may outlive their references).
- Driver (`tools/c2e`) accepts `--isystem <dir>`, `--report` now prints the
  three-way classification counts (translated / floor-extern / cross-TU), and
  `--floor-out <file>` writes the floor symbol list as the per-package link
  contract. On the real raylib probes: rcore 147 floor / 36 cross-TU,
  rshapes 9/7, rtext 66/36, rtextures 75/30 — the rshapes floor list is
  exactly the libm symbols (`cosf`, `sinf`, `powf`, ...).
- Package manifests accept `[ffi] floorSymbols = [...]` (parsed, round-tripped
  by the manifest writer): a documentation/review surface for floor thickness;
  the linker remains the enforcement backstop. The raylib-c2e regen script now
  writes the list into `eidos.toml` automatically.
- New parity-gate test `C2E_ExternClassification_SystemVsProjectHeader`
  asserts the classification against `-I` vs `-isystem` headers.
